# 规定规模性能验证 v0.6

日期：2026-10-12。对应需求草案 NFR06。本轮增加可复现数据与测量脚本，未修改业务计算规则、数据库结构或界面实现。

两组固定数据在本机均达到“计算核心小于10秒”的草案目标。47项计算/存储检查和15项浏览器检查通过，共62项。本结果是这两组固定拓扑的实测，不是所有同规模BOM、所有电脑或并发用户的性能保证，也不代表E3—E5最终验收完成。

## 1 测试环境和数据

| 项目 | 实际记录 |
|---|---|
| 操作系统 | Windows 11，build 26200 |
| CPU | Intel Core i7-14650HX，24个逻辑处理器 |
| Python / SQLite | 3.12.14 / 3.53.1 |
| 浏览器 | 无界面 Microsoft Edge 155.0.4283.45 |
| 实现方式 | Python标准库，过程式函数，SQLite本地保存 |

两个数据集均含200种物料、500条不同且有效的BOM边、100项全部参与的任务；所有物料都可从任务根节点到达，没有用无关记录凑足数量。数量采用整数，三个优先级交错，交货日期分布在17天内，输入使用固定种子20261012。

| 数据集 | 结构与目的 | 最长路径 |
|---|---|---|
| shared-stock | 20/40/60/80个物料组成4个层次，存在共享组件、已有库存和占用量，覆盖库存竞争与采购凑整 | 3条BOM边 |
| deep-zero-stock | 20个根、9个各含10件的自制层、90个外购叶子；中间以链为主，末层分叉，零库存迫使完整展开 | 10条BOM边 |

深度统一按“从根到叶经过的BOM边数”计算，因此深度10包含11个物料层次。深层数据用于验证深度边界，不冒充层层密集交叉的最坏情况。

两个数据集的计划和库存基准日固定为 **2026-10-01**；交货日期是测试输入，不是课程截止日期或真实生产安排。

## 2 测量方法

1. 每组预热一次，随后独立计时5次。核心计时覆盖 `calculate_plan` 的校验、拓扑处理、库存、采购、日期风险及完整来源记录构造；不包含生成输入、哈希核对、保存、网络或页面显示。
2. 使用 `perf_counter`，计时前回收上一轮对象，计算期间保持Python垃圾回收开启；所有原始采样值保存在证据JSON中。
3. 每组另测3次WSGI应用调用，包含请求JSON解析、完整计算、SQLite提交与响应JSON序列化。数据库初始化在计时外；这是适配层测量，不包含HTTP网络传输。
4. 每组在真实本机HTTP和Edge中操作一次“生成计划”和“查看历史”，等待结果摘要实际进入视口。此处包含自动化操作、渲染和滚动，只是单次交互观测，不作稳定延迟或百分位承诺。
5. 测试使用独立临时数据库，结束后清理。没有向正式数据库写入性能任务、库存或历史计划。

## 3 实测结果

单位：秒；数值保留三位小数。

| 指标 | 共享组件与库存 | 10层BOM、零库存 |
|---|---:|---:|
| 核心计算最小值，5次 | 0.239 | 0.222 |
| 核心计算中位数，5次 | 0.240 | 0.222 |
| 核心计算最大值，5次 | 0.241 | 0.233 |
| WSGI计算、提交、序列化中位数，3次 | 0.549 | 0.527 |
| WSGI计算、提交、序列化最大值，3次 | 0.551 | 0.549 |
| 单次已存批次数据库读取与解析 | 0.079 | 0.102 |
| 点击生成至摘要进入视口，1次 | 1.867 | 1.737 |
| 点击历史查看至摘要进入视口，1次 | 3.033 | 3.136 |

历史交互还包括浏览器寻找并滚动到页面下方的按钮和重新滚动到结果区，不能把该值当成数据库查询耗时。

| 输出规模 | 共享组件与库存 | 10层BOM、零库存 |
|---|---:|---:|
| 生产计划行 | 1,375 | 1,000 |
| 非零采购建议行 | 1,241 | 1,478 |
| 采购日期桶，含余量满足的零采购行 | 1,248 | 1,478 |
| 库存分配记录 | 4,823 | 5,000 |
| BOM来源记录 | 6,844 | 5,000 |
| 响应JSON，字节 | 9,281,065 | 10,049,678 |
| 三个历史批次的临时数据库，字节 | 26,517,504 | 28,864,512 |

两组分别有0项交期风险，这是固定日期输入的结果，不是省略风险计算。五类CSV均实测序列化耗时和字节数，最大的一次为共享数据的来源明细导出，约0.078秒；该时间不包括网络下载。

## 4 正确性与界面核对

47项核心/适配层检查涵盖规定规模、完整可达性、无环与深度、五次结果一致、每次小于10秒、输入不变、反转四张表行序后完整结果相同、库存逐条守恒、采购/缺口/最终余量守恒、余量不向过去日期流动，以及三次保存和历史读取完整。

零库存数据另用独立的“按物料聚合传播数量”算法计算预期，不调用规划器或其叶子函数、不建立BOM路径，核对200种物料的总毛需求。

15项浏览器检查涵盖两组基础数据保存、200行物料与100项勾选任务、成功生成、生产/采购/库存/来源表全部行数、摘要任务数、历史生产行完整、390像素页面无横向溢出，以及无未处理脚本错误。1440像素结果截图已查看；本轮未进行并发压测，也未修改分页行为。

## 5 复现与使用

在 `material-planning` 目录执行：

```powershell
python verify_performance.py
node verify_performance_ui.cjs
```

第一个脚本默认5次核心采样，可用 `--repeats 3` 至 `--repeats 20` 调整；会重新写入性能证据与两个固定数据集。第二个脚本依赖本机已有的Playwright与Edge，脚本顶部记录了本机Node依赖及Python路径，换机时需调整。测试端口为8769；正常工作台继续使用8765。

若本机没有配置python命令，可以使用README中的完整Python路径。浏览器验证沿用已有Web开发技能的验证流程；当前没有可用的agent-browser工具，实际使用Playwright与Edge执行，不将替代工具写成agent-browser结果。

可供页面导入的四表CSV压缩包：

- [共享组件与库存数据](../../material-planning/results/performance-shared-stock-csv.zip)
- [10层BOM与零库存数据](../../material-planning/results/performance-deep-zero-stock-csv.zip)

导入方法：解压后选择全部四个CSV文件，将计划基准日设为2026-10-01，校验并应用，点击任务“全选”后生成计划。新导入任务不会自动勾选。导入会替换当前编辑区所选表，需要保留现有编辑时应先保存。
